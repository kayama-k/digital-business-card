# デジタル名刺アプリ 要件定義

更新日：2026-09-21
ステータス：第1段階（公開名刺）の要件は確定。管理機能は第2段階以降で検討する。

この文書は、要件と実装方針に関する確定事項を一元管理する。

## 1. 目的

交流会などでQRコードから開ける、個人用の縦型デジタル名刺を提供する。第1段階では、閲覧者がプロフィールとポートフォリオを心地よく確認できる公開画面を提供する。名刺の所有者がブラウザから内容と演出を更新する管理機能は、第2段階以降で検討する。

## 2. 利用者と利用場面

| 利用者 | 主な利用場面 | 主な操作 |
| --- | --- | --- |
| 名刺の閲覧者 | QRコードやURLから名刺を開く | プロフィール・ポートフォリオの閲覧、保存、共有、QRコードの利用 |
| 名刺の編集者（第2段階以降） | PCまたはスマートフォンのブラウザから名刺を更新する | 内容・素材・動きの編集、リアルタイムプレビュー、下書き保存、公開 |

## 3. 段階別の提供範囲

| 段階 | 提供するもの | 提供しないもの |
| --- | --- | --- |
| 第1段階 | GitHub Pagesで公開する、設定ファイル駆動の公開名刺。プロフィール／ポートフォリオ切替、保存・共有、PNG・PDF出力、QRコード、画面遷移と波形アニメーションを含む。 | ログイン、管理画面、ブラウザ上の編集・保存、公開状態の変更、画像アップロード、API、DB。 |
| 第2段階以降 | 管理画面、認証、名刺データと素材の管理、下書き保存、公開・公開停止などを要求分析したうえで導入する。 | 実現時期・詳細な機能範囲は未定。 |

第1段階の文言、URL、配色、アニメーション値はリポジトリ内の設定データで管理し、画像素材は定めたアセットのパスを差し替えて更新する。画面上の切替・アニメーション・保存／共有はブラウザ上で実行するため、バックエンドを必要としない。

第1段階の公開URLにはGitHub Pagesの標準URLを使用し、独自ドメインは取得後に設定する。GitHubリポジトリは公開（Public）とする。

## 4. 技術方針

| 層 | 採用技術 | 役割 |
| --- | --- | --- |
| フロントエンド | React、TypeScript、Vite、CSS | 公開名刺、画面遷移とアニメーション。第2段階以降は編集画面とプレビューにも使用する。 |
| バックエンド（第2段階以降） | サポート中のJava LTS、Spring Boot | REST API、認証・認可、公開状態の制御、画像・名刺データの管理 |
| 永続化（第2段階以降） | PostgreSQL、Spring Data JPA、Flyway | 名刺・編集設定・公開状態の保存、スキーマ変更の管理 |
| API契約（第2段階以降） | OpenAPI | フロントエンドとバックエンド間の入出力を明文化する |

- CSSは通常のCSSとCSS変数を基本とし、Tailwind CSSは採用しない。
- 第1段階の公開先はGitHub Pagesとする。第1段階ではAPIとPostgreSQLを使用しない。
- 第2段階以降にJava APIを導入する場合、GitHub Pagesとは別の実行環境にAPIとPostgreSQLを配置する。APIの接続先は環境変数で管理し、秘密情報をフロントエンドへ含めない。

## 5. 公開名刺の機能要件（第1段階・確定）

### 5.1 表示

- ログイン不要で閲覧できる、モバイル優先の縦型デジタル名刺を提供する。
- プロフィールとポートフォリオを切り替えられる。
- 名刺アプリへの入口QRコードと、ポートフォリオへのQRコードを各URL設定値から生成する。
- タイトルはSVGアウトライン素材を使用し、適切な代替テキストを提供する。
- 画像素材は、定めたアセットのパスを差し替えて更新できる。
- タイトルはKatakanaboy / RをWebフォント化せず、SVGアウトラインとして使用する。
- プロフィール画像は`public/images/profile.png`に配置し、同パスで差し替えられるようにする。

### 5.2 保存・共有

- 保存・共有操作は別画面へ遷移せず、ボトムシートとして表示する。
- PNGは、リポジトリに事前配置した`public/images/non-business-card.png`（`1024 × 1536px`）を保存できる。PNGを更新した場合は、この素材も差し替えてGitHub Pagesへ公開する。
- PDFは同じ保存用デザインを、1ページ・2:3比率で保存できる。
- Web Share APIが利用できない場合は、公開URLをコピーする代替手段を提供する。

### 5.3 画面遷移と波形

- プロフィールとポートフォリオの切替時のみ、横方向の画面遷移と青い波形を同時に開始する。
- 保存・共有のボトムシート表示時には波を動かさない。
- 波形は一度だけ動き、開始・終了の基準形状を同一にする。
- 基準値は、全体時間1.3秒、振幅19（SVG viewBox基準）、長い減衰、ゆっくり始まりゆっくり終わるイージングとする。
- OSまたはブラウザの`prefers-reduced-motion`を尊重する。

詳細は[animation-spec.md](animation-spec.md)を正とする。

## 6. 素材の確定事項

| 項目 | 正式な扱い |
| --- | --- |
| 紙テクスチャ | GitHubにある元画像 `public/images/paper-texture.jpg` を確認したうえで、`idea3_profile` の表示中 `base` レイヤーのクロップと塗りを再現した `public/images/base.png` を表示に使う。非表示の `background_building` は参照しない。 |
| 上下の波 | 表示中の `両端あしらい上部`／`両端あしらい下部` に含まれる各 `Vector 3` の輪郭を使用し、`#3E8AB0` を `base` に乗算した紙目は `public/images/base-blue.png` に保持する。 |

画面の見た目を比較するための2倍書き出しPNGは `docs/design-comps/` に置く。これらは実装参照用であり、公開アプリから読み込まない。
`base` を差し替えたときは `node scripts/build-blue-texture.mjs` で青い紙目を再生成する。

## 7. 名刺ビジュアルエディター（第2段階以降の検討候補）

この節は将来の要求分析のたたき台であり、第1段階の実装対象ではない。利用者数、名刺数、権限、編集自由度、公開フロー、素材運用、認証方式、公開基盤を改めて決定してから要件として確定する。

### 7.1 利用環境と共通要件

- 編集者は認証後、PC・スマートフォン双方のブラウザからエディターを利用できる。
- 編集、プレビュー、下書き保存、公開の全操作は両デバイスで完結できる。
- 編集内容は、スマートフォン幅の公開名刺プレビューへリアルタイムに反映する。
- PCでは編集項目とプレビューを並べて表示できる。スマートフォンでは編集項目をボトムシートまたはアコーディオンに収め、プレビューとの切替または連続表示を可能にする。
- ドラッグ操作を補助機能とし、スマートフォンではタップ可能な上下移動など、すべての操作に代替手段を用意する。

### 7.2 編集対象

- 名前、肩書き、自己紹介、所在地、リンク、SNS、ポートフォリオ情報
- プロフィール画像、タイトル素材、紙テクスチャなどの画像素材
- 配色、文字サイズ、余白、各要素の表示・非表示
- 公開状態（下書き、公開、公開停止）

### 7.3 アニメーション編集

- 利用者は、アニメーションを「なし」「やさしい波」「標準の波」「はっきりした波」など、視覚的なプリセットから選択できる。
- 選択したプリセットは、波の振幅、時間、減衰、イージングの設定値を一括で反映する。
- 詳細設定では、振幅、時間、減衰、イージングを個別に設定できる。個別変更後は状態を「カスタム」として扱う。
- 値には適切な上下限を設け、極端な動きや長すぎる遷移を防止する。
- プリセットまたは詳細値を変更すると、プレビューへ即時に反映できる。利用者が任意のタイミングで再生できるプレビューボタンも用意する。
- 選択中の設定が生む効果を、自然言語で表示する。例：振幅には「波の上下の揺れが自然に分かる強さ」、時間には「短いほど軽快、長いほどゆったりした印象」と表示する。
- 設定値の組合せから、現在の動きの要約を表示する。例：「現在の動き：やさしく、ゆったりした波。画面切替に合わせて穏やかに揺れ、約1.3秒で静止します」。
- `prefers-reduced-motion`が有効な利用者には、公開画面で動きを抑えることを明示する。

## 8. データと公開の考え方（第2段階以降の検討候補）

- 名刺の文言、URL、素材参照、配色、レイアウト、アニメーション設定、公開状態を名刺単位で保存する。
- 公開名刺は公開済みの設定のみを参照する。下書きは閲覧者に公開しない。
- フロントエンドはAPI通信を`api/`層に集約し、UIコンポーネントから直接HTTP通信を行わない。
- API仕様はOpenAPIで管理し、フロントエンドが使用する型との不整合を防ぐ。

## 9. 非機能要件

- モバイル優先かつPCでも操作しやすいレスポンシブデザインとする。
- キーボード操作、フォーカス表示、適切な代替テキスト、動きの抑制設定を考慮する。
- 第1段階では、秘密情報をフロントエンドへ含めない。
- 第2段階以降に画像アップロード、認証、APIを導入する場合は、未認証者が編集・公開操作を行えない認可と安全な素材管理を実装する。

## 10. 第2段階以降の保留事項

| 項目 | 現在の状態 | 次に決める内容 |
| --- | --- | --- |
| 認証方式 | 編集者の認証が必要。具体方式は未決定。 | 利用者数、ログイン方法、セッションまたはトークンの方式 |
| エディターのレイアウト自由度 | 配色・余白・表示制御は対象。自由配置の必要性は未決定。 | テンプレート選択型にするか、要素を自由配置できるようにするか |
| 画像保存先 | 将来は画像管理が必要。 | 保存容量、運用費、外部ストレージの採用 |
| 公開基盤 | フロントとJava APIの分離は可能。 | GitHub Pages継続の可否と、API・DBの配置先 |
